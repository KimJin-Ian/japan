# 02. 핵심 사용자 흐름

## 1. 시나리오 A — 일본 한정상품을 사고 싶은 사람 (우선 구현)

```
검색엔진 ──▶ 상품 상세 ──▶ (저장) ──▶ 구매 부탁 CTA ──▶ 겸사겸사 부탁 작성 ──▶ 부탁 등록 ──▶ 매칭 ──▶ 거래 완료
 네이버·구글   product_view   product_save   request_click     gyeomsa_redirect       request_created  match_success  deal_completed
             └──────────── JAPAN FINDS가 측정 ───────────────┘ └────────── 겸사겸사가 검증해 전달 ──────────┘
```

| 단계 | 화면 | 사용자 행동 | 이벤트 | 이탈 방지 포인트 |
|---|---|---|---|---|
| 1 | 검색엔진 | "○○ 일본 한정" 검색 | – | 상품별 고유 URL, 한국어 제목·설명, 구조화 데이터 |
| 2 | 상세 | 이미지·한국어 상품명 확인 | `product_view` | 로그인·가입 요구 없음. 첫 화면에 한정 태그와 일본 가격 |
| 3 | 상세 | 한정 여부와 근거, 판매처 확인 | – | 근거 문장 + 공식 출처 링크 + 마지막 확인 시각. 불확실하면 '한정 여부 확인 중'으로 솔직하게 |
| 4 | 상세 | 일본 가격·한국 가격 확인 | – | 예상 원화 환산, 미포함 비용(배송비·세금·수수료) 명시, 한국가 없으면 '한국 가격 미확인' |
| 5 | 상세 | "한국에서는 못 산다 / 현지 매장에서만 판다"는 사실 인지 | – | 한국 공식 판매 여부와 구매 조건을 CTA 바로 위에 배치 |
| 6 | 상세 | 저장 (선택) | `product_save` | 로그인 없이 브라우저 저장 |
| 7 | 상세 고정 CTA | "일본 여행자에게 구매 부탁하기" 클릭 | `request_click` | 버튼 아래 한 줄로 "겸사겸사로 이동하며 상품정보가 미리 입력됩니다" |
| 8 | 겸사겸사 | 상품정보가 채워진 부탁 작성 화면 | `gyeomsa_redirect` | 상품명·브랜드·판매처·공식 URL 자동 입력 → 재입력 없음 |
| 9 | 겸사겸사 | 희망 구매일·수량·보수 입력 후 등록 | `request_created` | (겸사겸사 영역) |
| 10 | 겸사겸사 | 일본 여행자와 매칭·거래 | `match_success`, `deal_completed` | (겸사겸사 영역) |

겸사겸사 주소(`NEXT_PUBLIC_GYEOMSA_REQUEST_URL`)가 없을 때: 7단계 버튼이 "구매 부탁 출시 알림 받기"로 바뀌고, 신청은 `notify_requests`에 쌓인다. 이 신청 수가 출시 전 **구매 의향 검증 지표**가 된다.

## 2. 시나리오 B — 일본 여행을 준비하는 사람 (후속 확장)

| 단계 | 화면 | 행동 | 구현 시기 |
|---|---|---|---|
| 1 | 홈·목록 | 쇼핑 추천 상품 탐색, 지역 필터 | MVP |
| 2 | 상세·카드 | 관심 상품 저장 → 쇼핑리스트 | MVP (`/saved`) |
| 3 | 관심 상품 | "이 지역에 가시나요? 다른 사람의 부탁도 확인해 보세요" 안내 발견 | 후속 |
| 4 | 겸사겸사 | 여행 일정·방문 지역 등록 | 후속 (겸사겸사 측 기능) |
| 5 | 겸사겸사 | 일정에 맞는 구매 부탁 확인·수락·수행 | 후속 |

MVP에서는 1~2단계만 제공한다. 3단계 이후는 겸사겸사의 여행 일정 등록 기능이 준비된 뒤 연결한다.

## 3. 관리자 검수 흐름

```
자동 수집(RSS·API) ─▶ product_candidates 적재 ─▶ LLM 분석(한국어 정리·분류) ─▶ 검수 대기(pending)
                                                                              │
                              ┌───────────────┬───────────────┬──────────────┘
                              ▼               ▼               ▼
                           승인(approved)   반려(rejected)  병합(merged, 기존 상품에 합침)
                              │
                              ▼
                products(draft) ─▶ 출처·가격·이미지 사용권 확인 ─▶ 게시(published) ─▶ 판매 종료(ended) 처리
```

| 단계 | 관리자 행동 | 확인 기준 |
|---|---|---|
| 후보 확인 | 원문 제목·출처 URL 열람 | 한국 사용자에게 의미 있는 상품인가 |
| AI 결과 검토 | 한국어 상품명·요약·브랜드·카테고리·한정 유형·날짜·판매처·가격 | 필드별 신뢰도 0.6 미만은 '확인 필요'로 표시됨 → 원문과 대조 |
| 중복 처리 | 중복 의심 상품과 비교 후 병합 | 같은 상품이면 새로 만들지 않고 출처·오퍼만 추가 |
| 수정 | 상품명·가격 수정 | 가격은 출처에서 직접 확인한 값만 입력 |
| 이미지 | 사용권 확인(미확인 / 보도자료 사용 가능 / 사용 불가) | 사용 불가·미확인이면 자체 일러스트(플레이스홀더)로 게시 |
| 게시 | 공식 출처 1개 이상 검증 후 승인 | AI 결과는 자동 공개되지 않는다 |
| 사후 관리 | 판매 종료 처리, 수집 로그에서 실패 확인 | 종료일이 지난 상품은 '판매 종료' 표기 |

## 4. 전환 퍼널과 핵심 지표

**핵심 지표: JAPAN FINDS 방문자 중 겸사겸사에서 실제로 구매 부탁을 등록한 사용자 비율**
= `request_created`(겸사겸사 검증, ref=japanfinds) 고유 사용자 수 ÷ JAPAN FINDS 고유 방문자 수

| 퍼널 단계 | 이벤트 | 측정 주체 | 검증 방식 |
|---|---|---|---|
| 상세 조회 | `product_view` | JAPAN FINDS | 클라이언트 측정 (익명 세션 id) |
| 저장 | `product_save` | JAPAN FINDS | 클라이언트 측정 |
| 부탁 버튼 클릭 | `request_click` | JAPAN FINDS | 클라이언트 측정 |
| 겸사겸사로 이동 | `gyeomsa_redirect` | JAPAN FINDS | 이동 직전 기록 + `ref` 값 발급 |
| 부탁 등록 완료 | `request_created` | **겸사겸사** | 서버 간 전달(서명된 요청). JF의 `ref`와 겸사겸사 부탁 id를 함께 전달 |
| 매칭 성공 | `match_success` | **겸사겸사** | 서버 간 전달 |
| 거래 완료 | `deal_completed` | **겸사겸사** | 서버 간 전달 |

규칙:
- 버튼 클릭(`request_click`)이나 이동(`gyeomsa_redirect`)을 부탁 등록·거래 완료로 세지 않는다.
- JAPAN FINDS의 상품 id와 겸사겸사의 부탁 id는 서로 다른 값이다. 둘은 `ref`(이동 시 발급하는 추적 값)로만 연결한다.
- 인기순 정렬·'인기' 표기는 `product_view`·`product_save`가 실제로 쌓인 뒤에만 켠다.
- 보조 지표: 상세 조회 → 부탁 클릭 비율, 저장 비율, (출시 전) 알림 신청 수. 목표 수치는 아직 정하지 않았다(미결 사항).
