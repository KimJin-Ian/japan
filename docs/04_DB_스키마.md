# 04. DB 스키마 초안

실행용 SQL: [`supabase/schema.sql`](../supabase/schema.sql) — 빈 Supabase 프로젝트의 SQL Editor에서 그대로 실행한다.
(아직 실제 Supabase에서 실행해 보지는 않았다. Phase 2 첫 작업으로 실행·검증한다.)
필드 이름은 `src/lib/types.ts`의 camelCase를 snake_case로 옮겼다.

## 1. 관계

```
collection_logs ──< product_candidates ──(승인·병합)──▶ products ──< product_sources
                                                          │
                                                          ├──< product_offers   (판매처·가격, 상품과 분리)
                                                          ├──< user_interests >── auth.users
                                                          ├──< conversion_events ··· ref ··· 겸사겸사 부탁 id
                                                          └──< notify_requests
exchange_rates (JPY→KRW, 확인 시각 포함)

events ──< event_changes        (일정·조건 변경 내역)
   └────< event_products >──── products   (일정 ↔ 상품)
```

## 3. types.ts 대응

| types.ts | DB |
|---|---|
| `Product.limited.{status,types,evidence}` | `products.limited_status`, `limited_types`, `limited_evidence` |
| `Product.offers[]` (`Offer`) | `product_offers` 행 (`checkedAt`→`checked_at`, `sameItemVerified`→`same_item_verified`, `productCode`→`product_code`) |
| `Product.sources[]` (`Source`) | `product_sources` 행 |
| `Product.visual` | `products.visual` (jsonb) |
| `Product.isDemo` / `editorPick` / `addedAt` | `is_demo` / `editor_pick` / `added_at` |
| `Candidate.ai` (`AiField<T>` 묶음) | `product_candidates.ai` (jsonb, 필드별 `{ value, confidence }`) |
| `Candidate.duplicateOf` / `imageRights` / `reviewStatus` | `duplicate_of` / `image_rights` / `review_status` |
| `CollectionLog.method` ("RSS"·"API"·"수동 등록") | `collection_logs.method` enum (`rss`·`api`·`manual`) — 화면에서 한국어로 바꿔 표시 |

| `EventItem.titleKo` / `titleJa` / `characters` / `kind` / `place` | `events.title_ko` / `title_ja` / `characters` / `kind` / `place` |
| `EventItem.startDate` / `endDate` | `events.start_date` / `end_date` (둘 다 없으면 '일정 미정 소식') |
| `EventItem.krScope` / `scopeQuoted` | `events.kr_scope` / `scope_quoted` |
| `EventItem.source` (`Source`) | `events.source_label` / `source_url` / `source_type` / `source_verified` (일정은 출처가 하나라 열로 펼쳤다) |
| `EventItem.noticeCheckedAt` / `linkCheckedAt` | `events.notice_checked_at` / `link_checked_at` |
| `EventItem.changes[]` (`at`·`before`·`after`) | `event_changes` 행 (`changed_at`·`before_text`·`after_text`) |
| `EventItem.productSlugs[]` | `event_products` 행 (slug가 아니라 product_id로 연결) |

types.ts에 없고 DB에만 있는 것(일정): `events.link_ok`, `collect_method`, `publish_status`, `published_at`.

types.ts에 없고 DB에만 있는 것: `products.publish_status`·`published_at`·`image_url`·`image_rights`, `product_candidates.raw_excerpt_ja`·검수자 정보. 프론트를 DB에 붙일 때 타입에 추가한다.

## 5. 데이터 무결성 규칙 (제약으로 강제)

| 규칙 | 구현 |
|---|---|
| 한정을 '확인됨'으로 표시하려면 유형과 근거가 있어야 한다 | `products.limited_verified_needs_evidence` |
| 일본 오퍼는 JPY, 한국 오퍼는 KRW | `product_offers.offer_currency_matches_country` |
| 가격 비교는 동일 상품으로 확인된 한국 오퍼만 | `same_item_verified is true` 조건(부분 인덱스 + 조회 조건) |
| 같은 출처 URL은 후보로 한 번만 적재 | `product_candidates.source_url_hash` unique |
| 부탁 등록·매칭·거래 완료는 겸사겸사가 보낸 것만 인정 | `conversion_events.verified_events_come_from_gyeomsa` |
| 겸사겸사가 같은 이벤트를 다시 보내도 한 번만 기록 | `conversion_events_gyeomsa_once` unique 인덱스 |
| "근거: 공식 원문 인용"은 한국 이용 범위가 확정된 일정에만 | `events.scope_quoted_needs_scope` |
| 같은 공지 URL은 일정으로 한 번만 등록 | `events.source_url_hash` unique |
| 일정 종료일은 시작일보다 앞설 수 없다 | `events.event_end_after_start` |
| 가격이 없으면 행을 만들지 않는다(임의 생성 금지) | `price not null` — '한국 가격 미확인'은 KR 오퍼가 없는 상태로 표현 |

## 6. 검색·필터 인덱스

| 용도 | 인덱스 |
|---|---|
| 한국어·일본어 상품명, 브랜드, 캐릭터 부분 일치 | `pg_trgm` GIN (`name_ko`, `name_ja`, `brand`, `character`) |
| 태그·한정 유형 필터 | 배열 GIN (`tags`, `limited_types`) |
| 카테고리·브랜드·지역 필터 | 게시 상품 한정 부분 인덱스 |
| 최신순 | `(publish_status, added_at desc)` |
| 인기순 | `product_popularity` 뷰(최근 30일 조회·저장 수 — 30일은 가정값). 서버에서 service role로 읽는다. 데이터가 쌓이기 전에는 화면에 노출하지 않는다 |

한국어·일본어는 기본 전문 검색(tsvector) 형태소 분석이 맞지 않아 trigram을 택했다. 상품 수가 크게 늘면 별도 검색 엔진을 검토한다.

## 7. RLS 정책 초안

| 테이블 | 익명(anon) | 로그인 사용자 | 관리자 | 서버(service role) |
|---|---|---|---|---|
| products | published만 읽기 | published만 읽기 | 전체 | 전체 |
| product_sources / product_offers | 게시 상품 것만 읽기 | 동일 | 전체 | 전체 |
| product_candidates | ✕ | ✕ | 전체 | 수집기가 적재 |
| collection_logs | ✕ | ✕ | 읽기 | 수집기가 기록 |
| user_interests | ✕ | 본인 것만 읽기·쓰기·삭제 | – | 전체 |
| exchange_rates | 읽기 | 읽기 | 읽기 | 스케줄러가 기록 |
| conversion_events | ✕ | ✕ | 읽기 | Route Handler가 기록 |
| notify_requests | ✕ | ✕ | 읽기 | Route Handler가 기록 |
| events | published만 읽기 | published만 읽기 | 전체 | 수집기·링크 점검이 기록 |
| event_changes | 게시 일정 것만 읽기 | 동일 | 전체 | 전체 |
| event_products | 일정·상품이 **둘 다** 게시일 때만 읽기 | 동일 | 전체 | 전체 |

- 관리자 판별: Supabase Auth 사용자의 `app_metadata.role = 'admin'` (`public.is_admin()`). `app_metadata`는 사용자가 스스로 바꿀 수 없다.
- 프로토타입의 `/admin`은 `proxy.ts` Basic 인증이다. Phase 2에서 Supabase Auth 관리자 로그인으로 바꾸면 위 정책이 그대로 적용된다.
- service role 키는 서버·수집기 환경변수에만 둔다. 브라우저에 노출하지 않는다.

## 8. JAPAN FINDS 상품 id ↔ 겸사겸사 부탁 id

```
[상세 CTA 클릭]  JF: request_click 기록
      │
      ▼
[이동]  JF: ref(uuid) 발급 → gyeomsa_redirect 기록(product_id, ref)
        겸사겸사 URL 쿼리: product_id · name · brand · seller · source_url · ref
      │
      ▼
[겸사겸사에서 부탁 등록]  겸사겸사 → JF 서버 간 전달(서명 검증)
        { event: request_created, ref, gyeomsa_request_id }
        → conversion_events 에 origin='gyeomsa' 로 기록
```

- 두 id는 서로의 DB에 FK로 묶지 않는다. `ref`로만 대응시킨다.
- `gyeomsa_request_id`는 외부 값이라 text로 저장한다(형식은 겸사겸사 쪽에서 정함 — 미결).
- 서버 간 전달 방식(서명 방식, 재전송 규칙)은 겸사겸사 API 설계 때 확정한다.

## 9. 미결 사항

- `notify_requests.contact`에 무엇을 받을지(이메일 / 휴대폰 / 카카오) — 개인정보 수집 동의 문구와 보관 기간 필요.
- 익명 저장(localStorage)을 로그인 후 `user_interests`로 옮기는 시점과 방법.
- 환율 제공처와 갱신 주기.
- 인기 집계 기간(현재 30일은 가정).
- 일정 후보를 어디에 쌓을지: 지금은 수집된 공지가 `product_candidates`로만 들어간다. 일정용 후보 테이블을 따로 둘지, `product_candidates`에 종류 열을 더할지는 Phase 3에서 정한다.
- 일정의 `link_checked_at` 점검 주기와, 링크가 죽었을 때(`link_ok = false`) 화면에 어떻게 알릴지.
- `schema.sql`의 일정 블록도 실제 Supabase에서 아직 실행해 보지 않았다.
